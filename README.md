# ITSM Incident Analytics — BI report on GitHub Pages

A mini **BI stack** in a single repo: Python/pandas **ETL** over the
[Kaggle ITSM dataset](https://www.kaggle.com/datasets/ahanwadi/itsm-data) → JSON aggregates →
an interactive **D3.js** dashboard → deployed to **GitHub Pages** by **GitHub Actions** (CI/CD).

The report is **bilingual (EN ⇄ PT-BR)** — switch in the header, choice remembered.

## Features

- **ETL** (`etl/`) — extract → transform → load in pandas, with a validation gate that fails the pipeline on broken outputs
- **Dashboard** (`report/`) — KPI strip, ITIL service-operation metrics (MTTR, MTBF, FCR, escalation rate, SLA compliance, backlog), and 8 D3.js charts; D3 is vendored, no CDN or build step
- **i18n** — every string in `report/i18n.js`; add a language by adding one block + one button
- **CI/CD** — every push to `main` re-runs the ETL, validates the outputs and redeploys Pages; manual + monthly triggers included

## Architecture

```
data/raw/ITSM_data.csv   raw dataset (committed → CI needs no credentials)
        │
        ▼
etl/  extract.py   → obtains the CSV (local file, or Kaggle API if missing + secrets set)
      transform.py → cleans & aggregates (pandas) + ITIL measures
      load.py      → writes report/data/*.json
      pipeline.py  → orchestrates the three stages + validation gate
        │
        ▼
report/  index.html + i18n.js + charts.js (D3.js v7, vendored) + data/*.json
        │
        ▼
.github/workflows/bi-cicd.yml → ETL → validate → upload artifact → deploy Pages
```

## Run locally

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r etl/requirements.txt

python etl/pipeline.py            # extract → transform → load

cd report && python3 -m http.server 8000
# open http://localhost:8000      (a server is needed: the report fetches JSON)
```

## Deploy to GitHub (step by step)

1. **Create an empty repository** on GitHub (no README/.gitignore/license — this repo
   already has them). With the [GitHub CLI](https://cli.github.com/):
   ```bash
   gh repo create itsm-bi-report --public --source . --remote origin --push
   ```
   or the classic way:
   ```bash
   git remote add origin git@github.com:YOUR_USER/YOUR_REPO.git
   git push -u origin main
   ```

2. **Enable Pages with Actions as the source** (one time):
   `Settings → Pages → Source → GitHub Actions`.

3. **Trigger a run** — the workflow starts automatically on push; or go to the
   **Actions** tab → *BI pipeline & report deploy* → **Run workflow**.

4. **Open the report**: after the green run, it is live at
   `https://YOUR_USER.github.io/YOUR_REPO/`.

5. **Polish (2 minutes)**:
   - Replace `YOUR_USER/YOUR_REPO` in the badge URLs at the top of this README.
   - Put your name in `LICENSE`.
   - (Optional) `Settings → Rules → Rulesets`: require pull requests + the
     *BI pipeline & report deploy / ETL* check before merging to `main`.

### Optional: refresh data from Kaggle in CI

The raw CSV is committed, so CI needs **no secrets**. If you ever remove `data/raw/`
and want the pipeline to pull a fresh copy from Kaggle, add two repository secrets
(`Settings → Secrets and variables → Actions`): `KAGGLE_USERNAME` and `KAGGLE_KEY`
(from kaggle.com → Settings → *Create New Token*). `etl/extract.py` picks them up automatically.

### Troubleshooting

| Symptom | Fix |
| --- | --- |
| Deploy job fails with *"Get Pages site failed"* / 404 | Step 2 above — Pages source must be **GitHub Actions**, not "Deploy from a branch". |
| Deploy job fails with *"Resource not accessible by integration"* | Check the workflow still has `permissions: pages: write` + `id-token: write` on the deploy job. |
| ETL job fails in *Validate report data* | The pipeline produced empty/missing JSON — read the *Run ETL pipeline* log; a validation message says which assertion failed. |
| Report loads but shows *"Failed to load report data"* | JSON missing in the deployed artifact — confirm the ETL step ran in the same workflow. |
| Charts blank locally | You opened `index.html` via `file://` — serve it over HTTP (see *Run locally*). |

## CI/CD details

| Trigger | When |
| --- | --- |
| `push` to `main` touching `etl/`, `data/`, `report/` or the workflow | automatic |
| `workflow_dispatch` | manual, from the Actions tab |
| `schedule` (`0 6 1 * *`) | 1st of each month, 06:00 UTC |

Jobs: **etl** (checkout → setup Python 3.13 with pip cache → install deps → run pipeline →
validate ≥10 JSON files + `index.html` → upload `report/` as the Pages artifact), then
**deploy** (needs `etl`, uses `actions/deploy-pages@v4` with the default `GITHUB_TOKEN` —
no personal access token required).

## Data notes (what the ETL handles for you)

- Timestamps come in **two day-first formats** (`D/M/YYYY H:MM` and `DD-MM-YYYY H:MM`);
  both are normalised with `format="mixed", dayfirst=True` (0 negative durations).
- Priority/Impact/Urgency run **1–5** (5 = very low); `NS` impact marks unknown priority.
- `Handle_Time_hrs` uses an unreliable digit-grouping format, so resolution time is
  **recomputed** from `Open_Time` / `Resolved_Time`.
- **ITIL measures** (`report/data/itil.json`): MTTR, MTBF (biased by the volume ramp —
  indicative only), First Contact Resolution (% of resolved never reassigned — proxy),
  escalation rate, SLA compliance, reopen rate, major incidents (P1+P2), open backlog.
- **SLA targets are an assumption**, documented here and in the report:
  P1 ≤ 1d, P2 ≤ 3d, P3 ≤ 7d, P4/P5 ≤ 14d.
- The source extract only has resolution timestamps from Oct 2013 onward — earlier months
  legitimately show zero resolutions.

## Slide deck template (repo root `index.html`)

A self-contained HTML presentation: open it directly in a browser. Controls: `←` `→`
navigate, `F` fullscreen, `N` speaker notes; swipe on touch screens; browser Print exports
each slide to its own page. It lives in the repo but is **not** part of the Pages site
(the workflow publishes `report/` only).
